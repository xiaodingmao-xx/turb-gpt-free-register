# 通用 API 邮箱验证码可靠提取设计

## 背景

通用 API 邮箱接口可能返回纯文本、HTML 或 JSON。当前实现会在 JSON 没有明确 `code` 字段时，把所有值拉平成字符串，再对未经清理的 HTML 源码搜索任意六位数字。如果正常邮件解析没有命中，代码会无条件返回最后一个六位数字。

实际故障中，接口返回的 JSON 只有 `email`、`found`、`message` 和 `ok` 字段，`message` 是完整邮件 HTML。登录通知邮件没有验证码，但内联样式包含 `color: #000000`。当前兜底逻辑将该 CSS 色值识别为 OTP，settle 机制在五秒后返回它，注册重试又再次提交同一个错误值。真正的验证码邮件稍后到达后，第三轮才取得 `992669`。

## 目标

- 只从具有明确信任语义的字段或用户可见正文中提取验证码。
- 保持对明确 JSON 验证码字段、纯六位文本、普通文本和 HTML 邮件的兼容。
- HTML、CSS、脚本、属性和模板数字不得成为验证码候选。
- 已被验证页面拒绝的候选不得在同一次注册流程中重复提交。
- 只有可信候选才能启动 settle 倒计时。
- 日志应准确反映验证码的实际提取来源。

## 非目标

- 不改变 Outlook、gptmail、yangyang、mailnest、cloudmail 等其他邮箱来源的业务流程。
- 不通过维护一份“看起来可疑”的验证码黑名单解决问题。
- 不重构注册流程中与邮箱 OTP 无关的浏览器自动化代码。
- 不要求当前通用 API 增加时间戳、主题或独立验证码字段。

## 方案比较

### 方案一：封禁 `000000`

改动最小，但只能处理当前色值。`#111111`、`#202020` 等其他六位 CSS 色值仍会误判，也可能错误拒绝接口明确返回的真实验证码。不可采用。

### 方案二：严格解析可信字段和可见正文

区分 JSON 验证码字段、纯文本和 HTML；HTML 必须转为可见文本后才能提取，禁止对原始 HTML 执行任意六位数字兜底。同时在注册流程中排除已经提交失败的候选。该方案兼容现有接口并直接消除根因，采用此方案。

### 方案三：为当前接口编写专用客户端

可以精确适配 `email/found/message/ok`，但会降低通用 API 模块的通用性，每增加一个接口都需要新增适配器。当前没有必要采用。

## 提取架构

验证码候选按信任级别依次处理。

### 1. 明确的 JSON 验证码字段

检查以下字段：

- `code`
- `otp`
- `verification_code`
- `verificationCode`
- `email_code`
- `emailCode`

字段值必须完整匹配 `^\d{6}$`，不能从更长字符串中截取六位数字。明确字段具有最高信任级别，不使用 `000000` 等值黑名单。

### 2. 当前接口的信封状态

对于包含 `ok`、`found` 和 `message` 的响应：

- `ok` 明确为 `false` 时，本轮没有候选。
- `found` 明确为 `false` 时，本轮没有候选。
- `message` 如果包含 HTML，则按 HTML 可见正文处理。
- `message` 如果是纯文本，则按普通文本处理。

不得把 `email`、布尔状态或其他元数据与邮件正文拼接后共同扫描。

### 3. HTML 可见正文

新增单一职责的 HTML 到可见文本转换函数，执行：

1. 删除 `style`、`script`、`head` 及其内容。
2. 删除剩余标签和所有标签属性。
3. 解码 HTML 实体。
4. 归一化空白。

验证码提取只接收转换后的可见文本。不能在任何后续兜底中重新扫描原始 HTML。

### 4. 纯文本

- 去除首尾空白后整个响应恰好是六位数字时，直接接受。
- 含有其他内容时，六位数字必须位于 `code`、`verification`、`验证码`、`認証` 等 OTP 上下文附近。
- 没有上下文的孤立六位数字返回 `None`。

### 5. 删除危险兜底

删除“找不到上下文时返回最后一个六位数字”的行为。没有可信候选时返回 `None`，让调用者继续轮询。

## 数据流

1. `fetch_latest_otp` 获取 HTTP 响应。
2. 响应是 JSON 时，先检查明确验证码字段。
3. 如果是信封式响应，只解析 `message`，不扫描整个 JSON。
4. `message` 是 HTML 时先转换为可见文本；是纯文本时直接进入严格文本解析。
5. 只有可信候选才进入 `best_otp` 并启动 settle。
6. settle 期间发现不同可信候选时替换并重新计时。
7. 页面拒绝验证码后，注册流程将该候选加入本次流程的排除集合。
8. 下一轮获取验证码时传入排除集合，避免重复提交同一失败值。

## 重试行为

注册 OTP 循环新增局部 `rejected_codes` 集合。验证码提交后页面明确未接受时，将当前候选加入集合；下一轮调用 `wait_for_otp` 时通过 `exclude_codes` 传递。

该集合只在当前注册流程中生效，不持久化，也不影响其他账号。页面已经离开验证码流程或被判断为接受时，不加入集合。

如果接口持续只返回被排除候选，客户端保持轮询，直到出现新候选或达到原有超时时间。不得因为被排除候选启动 settle。

## 时间与邮件身份限制

接口提供时间字段时，继续使用 `after_ts` 过滤旧邮件。接口没有时间字段时，不能声称已经完成新旧邮件校验；安全性由严格正文提取、settle 和本次流程排除集合共同提供。

如果响应包含主题或发件人，应保留到诊断元数据中。缺少主题和发件人不直接拒绝，因为当前接口不提供这些字段；但正文中必须满足严格 OTP 规则。

## 日志

将模糊的 `source=structured_api` 细分为：

- `json_code_field`
- `html_visible_text`
- `plain_text`

日志继续记录时间和主题是否存在，但不得记录完整邮件 HTML、取件地址密钥或接口令牌。被排除候选只记录“已忽略本轮失败候选”，避免误导为接口没有返回内容。

## 测试设计

新增或扩展通用 API 邮箱测试，覆盖：

1. 登录通知 HTML 只含 `color: #000000`，结果为 `None`。
2. OTP HTML 同时含 `color: #000000` 和可见正文 `992669`，结果为 `992669`。
3. HTML 含多个六位 CSS 色值但没有 OTP，结果为 `None`。
4. `script` 或标签属性中的六位数字不被提取。
5. 纯文本 `992669` 可以提取。
6. 带验证码上下文的普通文本可以提取。
7. 无上下文的普通文本六位噪声不被提取。
8. JSON 明确 `code` 字段完整匹配时可以提取。
9. JSON `code` 字段包含更长数字或混合字符时不被截取。
10. `found=false` 或 `ok=false` 时不提取 `message` 中的数字。
11. 已排除候选不会进入 settle，后续新候选可以正常返回。
12. 注册第一次提交失败后，第二次取码会收到 `exclude_codes`。
13. 现有 yangyang、纯文本及验证码更新 settle 测试继续通过。

## 验收标准

- 使用故障邮件 HTML 复现时，解析结果不再是 `000000`，而是 `None`。
- 使用截图对应的 OTP 邮件 HTML 时，解析结果是 `992669`。
- 同一次注册任务不会连续提交已经被页面拒绝的验证码。
- 没有真实验证码时，程序继续轮询而不是在五秒后返回 CSS 数字。
- 相关单元测试与现有测试套件通过。
